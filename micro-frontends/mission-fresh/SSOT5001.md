## Application Overview

### Core Purpose
Mission Fresh is a comprehensive smoking cessation platform that helps users track their progress, manage cravings, and maintain their commitment to a smoke-free lifestyle. As an integral part of the main app (the-well-charged), it incorporates ALL quit-smoking functions and tools of the core platform. The application provides powerful tools for tracking health improvements, managing tasks related to quitting, overcoming withdrawal symptoms, and offering multi-faceted support during the quitting journey.

### Key Features
1. **Progress Tracking**: Monitor days smoke-free, health improvements, and achievements
2. **Task Management**: Complete tasks to maintain motivation and earn points
3. **Craving Management**: Tools and techniques to manage and overcome cravings
4. **Health Timeline**: Visualize health improvements over time
5. **Marketplace**: Access to smoking cessation products and support resources
6. **Withdrawal Management**: Tools for managing nicotine withdrawal symptoms
7. **Community Support**: Connect with others on their quit journey
8. **Medical Integration**: Connect with healthcare providers for medication support
9. **Alternative Therapies**: Access to evidence-based alternative therapies for smoking cessation
10. **Behavioral Tools**: Cognitive behavioral techniques to break smoking habits

### Integration Points
- Seamlessly interfaces with the Well-Charged ecosystem
- Can be used standalone or as part of the overall platform
- Shares authentication and user data with the main application while maintaining separate business logic
- Provides comprehensive quit-smoking functionality from the main app

### Rationale for Strict Consistency
1. Seamless integration between main app and micro-frontends
2. Simplified maintenance and debugging
3. Consistent developer experience
4. Prevention of version conflicts and dependency issues
5. Ensuring predictable behavior across all components of the system

## Database Strategy

### Table Naming Convention
All Mission Fresh tables MUST follow the standardized naming convention with "4" suffix:

- `mission4_progress`: User progress information
- `mission4_health_milestones`: Health improvement milestones
- `mission4_cravings`: Craving tracking and management
- `mission4_tasks`: Tasks related to quit journey
- `mission4_achievements`: User achievements and badges
- `mission4_products`: Marketplace products for cessation

### Database Schema

```sql
-- Progress tracking
CREATE TABLE mission4_progress (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id UUID REFERENCES auth.users(id) NOT NULL,
  date DATE NOT NULL,
  smoke_free BOOLEAN DEFAULT true,
  craving_intensity INTEGER CHECK (craving_intensity BETWEEN 0 AND 10),
  mood TEXT,
  notes TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  UNIQUE(user_id, date)
);

-- Health milestones
CREATE TABLE mission4_health_milestones (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  title TEXT NOT NULL,
  description TEXT NOT NULL,
  days_required INTEGER NOT NULL,
  icon_name TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);
```

### Row Level Security (RLS)

Mission Fresh uses simple RLS policies that enforce user-based access control:

```sql
-- Basic RLS policy for progress access
CREATE POLICY "Users can access only their own progress"
  ON mission4_progress
  FOR ALL
  USING (user_id = auth.uid());

CREATE POLICY "Health milestones are readable by all users"
  ON mission4_health_milestones
  FOR SELECT
  TO authenticated
  USING (true);

CREATE POLICY "Only admins can modify health milestones"
  ON mission4_health_milestones
  FOR ALL
  USING (
    auth.uid() IN (
      SELECT id FROM auth.users WHERE is_admin = true
    )
  );
```

## API Implementation

### Direct REST API Mandate

**IMPORTANT: This application MUST ONLY use direct REST API calls to interact with the database.**

Under NO circumstances should Supabase client methods be used. This applies to:
1. Database queries
2. Authentication flows
3. Storage operations
4. Real-time subscriptions

### Implementation Details

All API calls MUST be implemented through the `missionFreshApiClient.ts` file, which exposes functions for standard CRUD operations:

```typescript
// Example implementation of REST API client
export const getProgressData = async (
  userId: string,
  startDate: string,
  endDate: string,
  session: Session
): Promise<ProgressEntry[]> => {
  const response = await fetch(
    `${SUPABASE_URL}/rest/v1/mission4_progress?user_id=eq.${userId}&date=gte.${startDate}&date=lte.${endDate}&order=date.desc`,
    {
      headers: {
        apikey: SUPABASE_ANON_KEY,
        Authorization: `Bearer ${session.access_token}`,
        'Content-Type': 'application/json'
      }
    }
  );
  
  if (!response.ok) {
    const error = await response.json();
    throw new Error(error.message || response.statusText);
  }
  
  return await response.json();
};

export const addProgressEntry = async (
  entry: Omit<ProgressEntry, 'id' | 'created_at' | 'updated_at'>,
  session: Session
): Promise<ProgressEntry> => {
  const response = await fetch(
    `${SUPABASE_URL}/rest/v1/mission4_progress`,
    {
      method: 'POST',
      headers: {
        apikey: SUPABASE_ANON_KEY,
        Authorization: `Bearer ${session.access_token}`,
        'Content-Type': 'application/json',
        'Prefer': 'return=representation'
      },
      body: JSON.stringify(entry)
    }
  );
  
  if (!response.ok) {
    const error = await response.json();
    throw new Error(error.message || response.statusText);
  }
  
  return await response.json()[0];
};
```

## Authentication & Security

### Authentication Flow

Mission Fresh follows the same authentication strategy as the main application:

1. Users authenticate through the centralized auth system
2. JWT tokens are securely stored
3. Tokens are used for all API requests
4. Session data is passed to the micro-frontend via the mount configuration

### Security Guidelines

1. **Authorization Headers**
   - All API requests MUST include proper authorization headers
   - JWT tokens MUST be validated before accessing protected resources

2. **Data Validation**
   - All user inputs MUST be validated before processing
   - API responses MUST be validated before rendering

3. **Error Handling**
   - All API errors MUST be properly caught and handled
   - User-friendly error messages MUST be displayed

## Development Guidelines

### Code Organization

Mission Fresh follows these organization principles:

1. **Feature-Based Structure**
   - Components organized by feature rather than type
   - Each feature has its own directory with components, hooks, and utilities

2. **Component Patterns**
   - Presentational components in `/components`
   - Container components in `/containers`
   - Pages in `/pages`
   - Reusable hooks in `/hooks`
   - Utilities in `/utils`

### State Management

1. **Local State**
   - Use React's useState for component-specific state
   - Use useReducer for complex state logic

2. **Global State**
   - Use Zustand for global state management
   - Follow the same patterns as the main application

3. **API State**
   - Use custom hooks for API calls
   - Implement proper loading, error, and success states
   - Cache responses where appropriate

### Testing Requirements

All Mission Fresh components MUST have:
1. Unit tests for utility functions
2. Component tests for UI components
3. Integration tests for pages and complex features

### Performance Guidelines

1. **Loading Optimization**
   - Lazy-load routes and heavy components
   - Use React.memo for expensive renders
   - Implement virtualization for long lists

2. **API Efficiency**
   - Include only necessary fields in API requests
   - Batch related API calls where possible
   - Implement proper caching strategies
