## Application Overview

### Core Purpose
Care Connector is a comprehensive care coordination platform within the quit-smoking app "the-well-charged" that enables users to create and manage support groups, connect with care providers, manage tasks, and coordinate caregiving efforts. The platform facilitates communication and collaboration among individuals quitting smoking, their support network, and healthcare providers specialized in smoking cessation. This critical component of the quit-smoking journey empowers users to build the support systems necessary for successfully overcoming nicotine addiction.

### Key Features
1. **Quit Support Groups**: Create and manage groups focused on smoking cessation support
2. **Cessation Provider Marketplace**: Find and connect with healthcare providers specialized in quit-smoking programs
3. **Cessation Task Management**: Assign and track tasks related to the quitting process
4. **Quit Journey Coordination**: Communicate within support groups about smoking cessation challenges
5. **Withdrawal Management Planning**: Schedule support activities for challenging periods in the quit journey
6. **Relapse Prevention Support**: Connect with immediate support when experiencing strong cravings

### Integration Points
- Seamlessly interfaces with the Well-Charged quit-smoking ecosystem
- Can be used standalone or as part of the overall smoking cessation platform
- Shares authentication and user data with the main quit-smoking application while maintaining separate business logic
- Provides critical social support functionality for the smoking cessation journey

### Rationale for Strict Consistency
1. Seamless integration between main app and micro-frontends
2. Simplified maintenance and debugging
3. Consistent developer experience
4. Prevention of version conflicts and dependency issues
5. Ensuring predictable behavior across all components of the system

## Database Strategy

### Table Naming Convention
All Care Connector tables MUST follow the standardized naming convention with "8" suffix:

- `care8_groups`: Care group information
- `care8_group_members`: Group membership details
- `care8_group_invitations`: Invitation management
- `care8_group_tasks`: Tasks assigned within groups
- `care8_group_events`: Calendar events for groups
- `care8_providers`: Care provider information
- `care8_provider_reviews`: Reviews for care providers

### Database Schema

```sql
-- Group management
CREATE TABLE care8_groups (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name TEXT NOT NULL,
  description TEXT,
  created_by UUID REFERENCES auth.users(id) NOT NULL,
  is_private BOOLEAN DEFAULT true,
  avatar_url TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);

-- Group membership
CREATE TABLE care8_group_members (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  group_id UUID REFERENCES care8_groups(id) ON DELETE CASCADE NOT NULL,
  user_id UUID REFERENCES auth.users(id) NOT NULL,
  role TEXT NOT NULL DEFAULT 'member',
  joined_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  UNIQUE(group_id, user_id)
);
```

### Row Level Security (RLS)

Care Connector uses simple RLS policies that enforce user-based access control:

```sql
-- Basic RLS policy for group access
CREATE POLICY "Users can view groups they are members of"
  ON care8_groups
  FOR SELECT
  USING (
    auth.uid() IN (
      SELECT user_id FROM care8_group_members WHERE group_id = id
    )
    OR
    created_by = auth.uid()
  );

CREATE POLICY "Only creators can update groups"
  ON care8_groups
  FOR UPDATE
  USING (created_by = auth.uid());

CREATE POLICY "Only creators can delete groups"
  ON care8_groups
  FOR DELETE
  USING (created_by = auth.uid());
```

## API Implementation

### Direct REST API Mandate

**IMPORTANT: This application MUST ONLY use direct REST API calls to interact with the database.**

Under NO circumstances should Supabase client methods be used. This applies to:
1. Database queries
2. Authentication flows
3. Storage operations
4. Real-time subscriptions

### Implementation Details

All API calls MUST be implemented through the `careConnectorApiClient.ts` file, which exposes functions for standard CRUD operations:

```typescript
// Example implementation of REST API client
export const getGroups = async (
  session: Session
): Promise<Group[]> => {
  const response = await fetch(
    `${SUPABASE_URL}/rest/v1/care8_groups?select=*`,
    {
      headers: {
        apikey: SUPABASE_ANON_KEY,
        Authorization: `Bearer ${session.access_token}`,
        'Content-Type': 'application/json'
      }
    }
  );
  
  if (!response.ok) {
    const error = await response.json();
    throw new Error(error.message || response.statusText);
  }
  
  return await response.json();
};

export const createGroup = async (
  group: Omit<Group, 'id'>,
  session: Session
): Promise<Group> => {
  const response = await fetch(
    `${SUPABASE_URL}/rest/v1/care8_groups`,
    {
      method: 'POST',
      headers: {
        apikey: SUPABASE_ANON_KEY,
        Authorization: `Bearer ${session.access_token}`,
        'Content-Type': 'application/json',
        'Prefer': 'return=representation'
      },
      body: JSON.stringify({
        ...group,
        created_by: session.user.id
      })
    }
  );
  
  if (!response.ok) {
    const error = await response.json();
    throw new Error(error.message || response.statusText);
  }
  
  return await response.json()[0];
};
```

## Authentication & Security

### Authentication Flow

Care Connector follows the same authentication strategy as the main application:

1. Users authenticate through the centralized auth system
2. JWT tokens are securely stored
3. Tokens are used for all API requests
4. Session data is passed to the micro-frontend via the mount configuration

### Security Guidelines

1. **Authorization Headers**
   - All API requests MUST include proper authorization headers
   - JWT tokens MUST be validated before accessing protected resources

2. **Data Validation**
   - All user inputs MUST be validated before processing
   - API responses MUST be validated before rendering

3. **Error Handling**
   - All API errors MUST be properly caught and handled
   - User-friendly error messages MUST be displayed

## Development Guidelines

### Code Organization

Care Connector follows these organization principles:

1. **Feature-Based Structure**
   - Components organized by feature rather than type
   - Each feature has its own directory with components, hooks, and utilities

2. **Component Patterns**
   - Presentational components in `/components`
   - Container components in `/containers`
   - Pages in `/pages`
   - Reusable hooks in `/hooks`
   - Utilities in `/utils`

### State Management

1. **Local State**
   - Use React's useState for component-specific state
   - Use useReducer for complex state logic

2. **Global State**
   - Use Zustand for global state management
   - Follow the same patterns as the main application

3. **API State**
   - Use custom hooks for API calls
   - Implement proper loading, error, and success states
   - Cache responses where appropriate

### Testing Requirements

All Care Connector components MUST have:
1. Unit tests for utility functions
2. Component tests for UI components
3. Integration tests for pages and complex features

### Performance Guidelines

1. **Loading Optimization**
   - Lazy-load routes and heavy components
   - Use React.memo for expensive renders
   - Implement virtualization for long lists

2. **API Efficiency**
   - Include only necessary fields in API requests
   - Batch related API calls where possible
   - Implement proper caching strategies
