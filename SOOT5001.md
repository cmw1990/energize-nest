## 1. Introduction

### 1.1 Purpose of Mission Fresh

Mission Fresh (code name: SOOT5001) is a comprehensive food delivery and meal planning platform designed to connect fresh, local produce with consumers. The application enables users to:

- Browse and order fresh, locally-sourced produce and meal kits
- Create and customize meal plans based on dietary preferences and restrictions
- Schedule recurring deliveries of fresh produce and ingredients
- Track nutrition information and dietary goals
- Connect with local farmers and food producers
- Access recipes and cooking instructions for purchased ingredients
- Provide feedback and reviews on products and services

The platform aims to reduce food waste, support local agriculture, promote healthy eating habits, and make fresh food more accessible to communities.

### 1.2 Key Features

- **Marketplace**: Browse and purchase fresh, local produce and meal kits
- **Meal Planning**: Create, customize, and save meal plans
- **Delivery Management**: Schedule one-time or recurring deliveries
- **Nutrition Tracking**: Monitor nutritional intake and dietary goals
- **Producer Profiles**: Connect with local farmers and food producers
- **Recipe Database**: Access recipes and cooking instructions
- **Review System**: Provide feedback on products and deliveries
- **Subscription Management**: Manage recurring orders and subscriptions

### 2.3 Backend Authentication

The application uses Supabase for authentication and database access. Authentication is handled through JWT tokens obtained from Supabase Auth.

**Development Environment Variables**:
```
VITE_SUPABASE_URL=https://your-project-id.supabase.co
VITE_SUPABASE_ANON_KEY=your-anon-key
STRIPE_PUBLISHABLE_KEY=your-stripe-publishable-key
```

**Production Environment Secrets**:
> **SECURITY NOTE**: Never commit these values to GitHub or expose them in client-side code.
```
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key  # Only for secure server-side operations
STRIPE_SECRET_KEY=your-stripe-secret-key         # For payment processing
```

**API Authentication Flow**:
1. User signs in through Supabase Auth
2. JWT token is stored in local storage
3. Token is included in all API requests via the `apiRequest` function
4. Token validity is checked server-side through RLS policies

### 3.2 Table Schemas

#### 3.2.1 fresh_products

Stores information about available products.

```sql
CREATE TABLE fresh_products (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name TEXT NOT NULL,
  description TEXT,
  price DECIMAL(10, 2) NOT NULL,
  unit TEXT NOT NULL,
  stock_quantity INTEGER NOT NULL,
  producer_id UUID REFERENCES fresh_producers(id) ON DELETE CASCADE,
  is_organic BOOLEAN DEFAULT false,
  is_local BOOLEAN DEFAULT true,
  image_url TEXT,
  nutrition_info JSONB,
  seasonal_availability JSONB,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);
```

#### 3.2.2 fresh_categories

Stores product categories with optional hierarchy.

```sql
CREATE TABLE fresh_categories (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name TEXT NOT NULL,
  description TEXT,
  parent_id UUID REFERENCES fresh_categories(id) ON DELETE SET NULL,
  image_url TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);
```

#### 3.2.3 fresh_product_categories

Junction table to manage many-to-many relationship between products and categories.

```sql
CREATE TABLE fresh_product_categories (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  product_id UUID REFERENCES fresh_products(id) ON DELETE CASCADE,
  category_id UUID REFERENCES fresh_categories(id) ON DELETE CASCADE,
  UNIQUE(product_id, category_id)
);
```

#### 3.2.4 fresh_producers

Stores information about food producers and farmers.

```sql
CREATE TABLE fresh_producers (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id UUID REFERENCES auth.users(id),
  name TEXT NOT NULL,
  description TEXT,
  location TEXT,
  coordinates GEOGRAPHY(POINT),
  contact_email TEXT,
  contact_phone TEXT,
  website TEXT,
  logo_url TEXT,
  banner_url TEXT,
  is_verified BOOLEAN DEFAULT false,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);
```

#### 3.2.5 fresh_orders

Stores customer orders.

```sql
CREATE TABLE fresh_orders (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id UUID REFERENCES auth.users(id) NOT NULL,
  order_number TEXT UNIQUE NOT NULL,
  status TEXT DEFAULT 'pending' CHECK (status IN ('pending', 'processing', 'shipped', 'delivered', 'cancelled')),
  total_amount DECIMAL(10, 2) NOT NULL,
  payment_intent_id TEXT,
  payment_status TEXT DEFAULT 'pending' CHECK (status IN ('pending', 'paid', 'failed', 'refunded')),
  delivery_address_id UUID REFERENCES fresh_addresses(id),
  delivery_date TIMESTAMP WITH TIME ZONE,
  delivery_instructions TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);
```

#### 3.2.6 fresh_order_items

Stores items within an order.

```sql
CREATE TABLE fresh_order_items (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  order_id UUID REFERENCES fresh_orders(id) ON DELETE CASCADE,
  product_id UUID REFERENCES fresh_products(id),
  quantity INTEGER NOT NULL,
  unit_price DECIMAL(10, 2) NOT NULL,
  total_price DECIMAL(10, 2) NOT NULL,
  notes TEXT

```

#### 3.2.7 fresh_subscriptions

Stores recurring delivery subscriptions.

```sql

  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
```

## 4. Row-Level Security (RLS)

### 4.1 RLS Overview

Mission Fresh uses Row-Level Security (RLS) to control access to data at the database level. RLS policies are implemented to ensure users can only access data they are authorized to see or modify.

### 4.2 RLS Policies 

#### 4.2.1 fresh_products Table

```sql
-- Allow anyone to view all products
CREATE POLICY "Anyone can view products" 
ON fresh_products FOR SELECT 
USING (true);

-- Allow producers to create products
CREATE POLICY "Producers can create products" 
ON fresh_products FOR INSERT 
WITH CHECK (
  EXISTS (
    SELECT 1 FROM fresh_producers 
    WHERE fresh_producers.id = producer_id 
    AND fresh_producers.user_id = auth.uid()
  )
);

-- Allow producers to update their own products
CREATE POLICY "Producers can update their products" 
ON fresh_products FOR UPDATE 
USING (
  EXISTS (
    SELECT 1 FROM fresh_producers 
    WHERE fresh_producers.id = producer_id 
    AND fresh_producers.user_id = auth.uid()
  )
);

-- Allow producers to delete their own products
CREATE POLICY "Producers can delete their products" 
ON fresh_products FOR DELETE 
USING (
  EXISTS (
    SELECT 1 FROM fresh_producers 
    WHERE fresh_producers.id = producer_id 
    AND fresh_producers.user_id = auth.uid()
  )
);
```

#### 4.2.2 fresh_orders Table

```sql
-- Allow users to view their own orders
CREATE POLICY "Users can view their own orders" 
ON fresh_orders FOR SELECT 
USING (user_id = auth.uid());

-- Allow users to create orders
CREATE POLICY "Users can create orders" 
ON fresh_orders FOR INSERT 
WITH CHECK (user_id = auth.uid());

-- Allow users to update their own orders
CREATE POLICY "Users can update their own orders" 
ON fresh_orders FOR UPDATE 
USING (
  user_id = auth.uid() AND 
  status NOT IN ('delivered', 'cancelled')
);

-- Allow users to cancel their own orders
CREATE POLICY "Users can cancel their orders" 
ON fresh_orders FOR UPDATE 
USING (
  user_id = auth.uid() AND 
  status IN ('pending', 'processing') AND 
  NEW.status = 'cancelled'
);
```

#### 4.2.3 fresh_producers Table

```sql
-- Allow anyone to view producer profiles
CREATE POLICY "Anyone can view producer profiles" 
ON fresh_producers FOR SELECT 
USING (true);

-- Allow users to create a producer profile
CREATE POLICY "Users can create producer profiles" 
ON fresh_producers FOR INSERT 
WITH CHECK (
  user_id = auth.uid() AND 
  NOT EXISTS (
    SELECT 1 FROM fresh_producers WHERE user_id = auth.uid()
  )
);

-- Allow producers to update their own profile
CREATE POLICY "Producers can update their own profile" 
ON fresh_producers FOR UPDATE 
USING (user_id = auth.uid());
```

#### 4.2.4 fresh_reviews Table

```sql
-- Allow anyone to view all reviews
CREATE POLICY "Anyone can view reviews" 
ON fresh_reviews FOR SELECT 
USING (true);

-- Allow authenticated users to create reviews for products they've purchased
CREATE POLICY "Users can create reviews for purchased products" 
ON fresh_reviews FOR INSERT 
WITH CHECK (
  user_id = auth.uid() AND 
  product_id IS NOT NULL AND 
  EXISTS (
    SELECT 1 FROM fresh_order_items oi
    JOIN fresh_orders o ON oi.order_id = o.id
    WHERE o.user_id = auth.uid() 
    AND oi.product_id = product_id
    AND o.status = 'delivered'
  )
);

-- Allow users to update their own reviews
CREATE POLICY "Users can update their own reviews" 
ON fresh_reviews FOR UPDATE 
USING (user_id = auth.uid());

-- Allow users to delete their own reviews
CREATE POLICY "Users can delete their own reviews" 
ON fresh_reviews FOR DELETE 
USING (user_id = auth.uid());
```

#### 4.2.5 fresh_meal_plans Table

```sql
-- Allow users to view their own meal plans
CREATE POLICY "Users can view their own meal plans" 
ON fresh_meal_plans FOR SELECT 
USING (user_id = auth.uid());

-- Allow users to create meal plans
CREATE POLICY "Users can create meal plans" 
ON fresh_meal_plans FOR INSERT 
WITH CHECK (user_id = auth.uid());

-- Allow users to update their own meal plans
CREATE POLICY "Users can update their own meal plans" 
ON fresh_meal_plans FOR UPDATE 
USING (user_id = auth.uid());

-- Allow users to delete their own meal plans
CREATE POLICY "Users can delete their own meal plans" 
ON fresh_meal_plans FOR DELETE 
USING (user_id = auth.uid());
```

> *For brevity, policies for the other tables are not included here but follow a similar pattern.*

### 4.3 RLS Best Practices

1. **Principle of Least Privilege**: Grant the minimum permissions necessary for users to perform their tasks.
2. **Comprehensive Policies**: Ensure all tables have appropriate RLS policies for INSERT, SELECT, UPDATE, and DELETE operations.
3. **Policy Testing**: Test policies thoroughly with different user roles to ensure correct behavior.
4. **Simple Conditions**: Keep policy conditions simple to avoid performance issues.
5. **Documentation**: Document all policies and their intended purpose.

## 8. Troubleshooting

### 8.1 Common Issues and Solutions

#### Payment Processing Issues:

**Issue**: Payment intent creation fails.
**Solution**: Check Stripe API keys and webhook configuration.

#### Order Processing Issues:

**Issue**: Orders stuck in processing state.
**Solution**: Verify webhook handlers for payment confirmation.

#### Stock Management Issues:

**Issue**: Products showing as available despite being out of stock.
**Solution**: Check stock update procedures and implement locking mechanisms.

#### Delivery Zone Issues:

**Issue**: Customers able to place orders outside delivery zones.
**Solution**: Verify delivery zone checking logic in checkout process.
